<h2 id="-">روش بررسی</h2>
<br />
<p>ابتدا جست‌وجوی کد انجام شد و سپس فایل‌های منتخب Java، TypeScript و SQL مستقیماً خوانده شدند. وجود نام فایل یا route به‌تنهایی Implementation محسوب نشد.</p>
<br />
<p>در تمام فصل‌ها این تمایزها حفظ شده‌اند:</p>
<br />
<p>1. frontend presentation در برابر backend execution؛</p>
<p>2. software quality در برابر trade-goods quality؛</p>
<p>3. platform status در برابر external legal authority؛</p>
<p>4. وجود جدول در برابر lifecycle کامل؛</p>
<p>5. ذخیره idempotency key در برابر جلوگیری واقعی از duplicate؛</p>
<p>6. وجود tenant field در برابر tenant enforcement قابل اعتماد؛</p>
<p>7. status string در برابر state machine کنترل‌شده؛</p>
<p>8. فراخوانی Event publisher در برابر delivery تضمین‌شده و outbox.</p>
<br />
<h2 id="">محدودیت‌ها</h2>
<br />
<p>- Deployment این snapshot اثبات نشده است.</p>
<p>- وجود فایل Test به‌معنی اجرای موفق Test یا CI نیست.</p>
<p>- migrationها از روی source بررسی شده‌اند، نه اجرای مستقل.</p>
<p>- outcomeهای customs، carrier، inspector و warehouse فقط با authority evidence می‌توانند authoritative شوند.</p>
<p>- بخشی از controllerها direct JDBC دارند و هماهنگی runtime datasource با migration نیازمند integration test است.</p>

<h2 id="-inspection">صفحه Inspection</h2>

<h2 id="evidence-maturity">Evidence maturity</h2>
<br />
<p>Import Customs یکی از بالغ‌ترین بخش‌های بررسی‌شده در Wave 02 است.</p>
<br />
<p>Migration V16 این جدول‌ها را ایجاد می‌کند:</p>
<br />
<p>- <code class="code-inline">partner.import_declarations</code></p>
<p>- <code class="code-inline">partner.wms_inbound_orders</code></p>
<p>- <code class="code-inline">partner.wms_inbound_items</code></p>
<p>- <code class="code-inline">partner.warehouse_receipts</code></p>
<br />
<p>Controller یک lifecycle Partner-scoped دارد:</p>
<br />
<p>- list و detail؛</p>
<p>- create از Shipment متعلق به Partner؛</p>
<p>- generic update فقط در <code class="code-inline">DRAFT</code> و <code class="code-inline">CUSTOMS_HOLD</code>؛</p>
<p>- submit اختصاصی؛</p>
<p>- mark-duty-paid اختصاصی؛</p>
<p>- mark-cleared اختصاصی؛</p>
<p>- status history و audit؛</p>
<p>- sync وضعیت Shipment به <code class="code-inline">CUSTOMS_CLEARED</code>.</p>
<br />
<p>Classification: <code class="code-inline">IMPLEMENTED_WITH_GAP</code>.</p>
<br />
<h2 id="-">کنترل‌های مثبت</h2>
<br />
<p>- Partner ID از JWT principal گرفته می‌شود.</p>
<p>- بسیاری از read/writeها با Partner ID محدود می‌شوند.</p>
<p>- create بررسی می‌کند Shipment متعلق به Partner باشد.</p>
<p>- terminal status از generic PATCH ممنوع است.</p>
<p>- submit فقط از <code class="code-inline">DRAFT</code> مجاز است.</p>
<p>- clear به Shipment لینک‌شده نیاز دارد.</p>
<p>- audit snapshot و history ثبت می‌شود.</p>
<br />
<h2 id="gap-">Gapهای مهم</h2>
<br />
<p>1. Migration عمداً <code class="code-inline">partner.import_declarations</code> را DROP و recreate می‌کند؛ این رفتار destructive است.</p>
<p>2. <code class="code-inline">mark-duty-paid</code> از وضعیت <code class="code-inline">CLEARED</code> نیز مجاز است که lifecycle را غیرمنطقی می‌کند.</p>
<p>3. duty/tax صفر یا null فقط warning ایجاد می‌کند و عملیات را block نمی‌کند.</p>
<p>4. <code class="code-inline">mark-cleared</code> یک application action است و authority response خارجی اثبات نشده.</p>
<p>5. Shipment status با direct cross-table mutation تغییر می‌کند.</p>
<p>6. JDBC updateها optimistic version predicate ندارند.</p>
<p>7. status history در JSON mutable است.</p>
<p>8. Provider WMS tables با Warehouse/Inventory ownership هم‌پوشانی دارند.</p>
<br />
<h2 id="-canonical">مدل canonical</h2>
<br />

<p>- <code class="code-inline">DutyAssessmentObserved</code> — authority observation؛</p>
<p>- <code class="code-inline">DutyPaymentIntent</code> و <code class="code-inline">DutyPaymentOutcome</code> — Finance/Payment؛</p>

<br />
<p>هیچ کاربر برنامه نباید بدون authority evidence بتواند legal clearance بسازد.</p>

<h2 id="context-">Contextهای اجرایی</h2>
<br />
<p>دو Context اصلی وجود دارد:</p>
<br />
<p>1. <code class="code-inline">provider-service</code> برای Partner logistics و Booking؛</p>
<p>2. <code class="code-inline">shipping-service</code> برای <code class="code-inline">shipping.trade_shipments</code> و API حمل B2B.</p>
<br />
<p>مرزهای Booking، Shipment، Carrier Observation، Handover و Custody هنوز canonical نشده‌اند.</p>
<br />
<h2 id="booking">Booking</h2>
<br />
<p>Migration <code class="code-inline">partner.bookings</code> اطلاعات carrier، mode، vessel/flight، container، ports، dates، transit estimate، agent، confirmation، status، Partner و metadata را ذخیره می‌کند.</p>
<br />
<p>Export Handover Portal از API واقعی <code class="code-inline">/api/v1/logistics/bookings</code> استفاده می‌کند و این stateها را نمایش می‌دهد:</p>
<br />
<p>- <code class="code-inline">REQUESTED</code></p>
<p>- <code class="code-inline">CONFIRMED</code></p>
<p>- <code class="code-inline">LOADED</code></p>
<p>- <code class="code-inline">HANDED_OVER</code></p>
<p>- <code class="code-inline">CANCELLED</code></p>
<br />
<p>Portal همچنین pickup address، loading time، contact، seal number و referenceهای Packing List و Commercial Invoice را می‌گیرد.</p>
<br />
<p>این journey اجرایی مفید است، اما <code class="code-inline">HANDED_OVER</code> به‌تنهایی Custody Transfer معتبر نیست.</p>
<br />
<h2 id="trade-shipment">Trade Shipment</h2>
<br />
<p><code class="code-inline">TradeShipmentEntity</code> شامل این داده‌هاست:</p>
<br />
<p>- Purchase Order و Trade Order reference؛</p>
<p>- carrier و tracking number؛</p>
<p>- transport mode و booking reference؛</p>
<p>- master/house bill؛</p>
<p>- container count و forwarder؛</p>
<p>- origin/destination؛</p>
<p>- status، ETA و actual delivery؛</p>
<p>- weight، volume و package count؛</p>
<p>- metadata و tenant.</p>
<br />
<p>Service رفتار create، list/filter، get، update، tracking append، stats و Kafka send را دارد. Controller نیز <code class="code-inline">/api/shipping/trade/shipments</code> را ارائه می‌دهد.</p>
<br />
<p>Classification: <code class="code-inline">IMPLEMENTED_WITH_GAP</code>.</p>
<br />
<h2 id="-">یافته‌های بحرانی کد</h2>
<br />
<p>- هنگام ساخت Shipment Item، <code class="code-inline">tenantId</code> برابر Shipment UUID قرار داده می‌شود، نه tenant واقعی.</p>
<p>- list/get/update/track در Service بررسی‌شده tenant-scoped نیستند.</p>
<p>- items با <code class="code-inline">findAll()</code> گرفته و in-memory فیلتر می‌شوند.</p>
<p>- status string بدون transition guard است.</p>
<p>- tracking history در metadata JSON mutable ذخیره می‌شود.</p>
<p>- متد publish پارامتر <code class="code-inline">eventType</code> می‌گیرد، اما آن را داخل payload قرار نمی‌دهد.</p>
<p>- خطای Kafka catch و log می‌شود و DB transaction می‌تواند بدون Event موفق بماند.</p>
<p>- outbox تراکنشی پیدا نشد.</p>
<p>- delayed count برابر صفر hard-code شده است.</p>
<p>- observationهای carrier فاقد source event ID، observed/received time، confidence و correction lineage هستند.</p>
<br />
<h2 id="custody">Custody</h2>
<br />
<p>وضعیت <code class="code-inline">HANDED_OVER</code> در Booking و Portal دیده می‌شود، اما Aggregate مستقل Custody پیدا نشد.</p>
<br />
<p>Custody معتبر باید شامل این موارد باشد:</p>
<br />
<p>- Cargo/Package Set مشخص؛</p>
<p>- handing party و mandate؛</p>
<p>- receiving party و mandate؛</p>
<p>- time و location؛</p>
<p>- seal، package count و weight observation؛</p>
<p>- attestation دو طرف یا exception؛</p>
<p>- refusal/discrepancy؛</p>
<p>- correction؛</p>
<p>- onward transfer یا custody termination.</p>
<br />
<p>نتیجه: Booking و Shipment <code class="code-inline">IMPLEMENTED_WITH_GAP</code>؛ Custody <code class="code-inline">REFERENCE_ARCHITECTURE</code>.</p>

<h2 id="warehouse-service">Warehouse Service</h2>
<br />
<p><code class="code-inline">AsnEntity</code> این اطلاعات را ذخیره می‌کند:</p>
<br />
<p>- ASN number و reference؛</p>
<p>- Purchase Order، warehouse، tenant و supplier؛</p>
<p>- carrier و tracking؛</p>
<p>- pallet count، line count و expected quantity؛</p>
<p>- estimated/actual arrival؛</p>
<p>- dock appointment؛</p>
<p>- line items در JSON؛</p>
<p>- status و timestamps.</p>
<br />
<p><code class="code-inline">AsnService</code> رفتارهای زیر را دارد:</p>
<br />
<p>- create ASN؛</p>
<p>- update status؛</p>
<p>- link به Dock Appointment؛</p>
<p>- get/list/pending؛</p>
<p>- conflict detection برای dock؛</p>
<p>- create/check-in/complete/cancel appointment؛</p>
<p>- receiving summary.</p>
<br />
<p><code class="code-inline">AsnController</code> مسیرهای <code class="code-inline">/api/v1/warehouse/receiving</code> را ارائه می‌دهد.</p>
<br />
<p>Classification: <code class="code-inline">IMPLEMENTED_WITH_GAP</code>.</p>
<br />
<h2 id="provider-wms">Provider WMS</h2>
<br />
<p>Migration V16 در Provider schema نیز این‌ها را ایجاد می‌کند:</p>
<br />
<p>- <code class="code-inline">wms_inbound_orders</code></p>
<p>- <code class="code-inline">wms_inbound_items</code></p>
<p>- <code class="code-inline">warehouse_receipts</code></p>
<br />
<p>این مدل با Warehouse Service هم‌پوشانی دارد و وضعیت آن <code class="code-inline">CONFLICT_REQUIRES_CANONICALIZATION</code> است.</p>
<br />
<h2 id="gap-">Gapهای قطعی</h2>
<br />
<p>- ASN status مستقیماً از string درخواست پذیرفته می‌شود.</p>
<p>- get/update/link بر اساس ID، tenant scope آشکار ندارند.</p>
<p>- optimistic lock روی ASN یا Dock Appointment دیده نشد.</p>
<p>- Event/outbox برای اتصال Receiving به Inventory پیدا نشد.</p>
<p>- line items در TEXT/JSON ذخیره می‌شوند.</p>
<p>- summary تعداد کل dock door را همیشه ۱۰ فرض می‌کند.</p>
<p>- receipt line scan، package identity، damage evidence، quarantine، discrepancy و signed proof در Service بررسی‌شده وجود ندارند.</p>
<p>- Provider warehouse receipt می‌تواند به System of Record دوم تبدیل شود.</p>
<p>- Delivery/POD و Warehouse Receipt از هم به‌وضوح تفکیک نشده‌اند.</p>
<br />
<h2 id="-canonical">مرز canonical</h2>
<br />
<p>Warehouse باید Physical Receiving Execution و Receipt Observation را مالک باشد. Inventory باید Stock Position را مالک بماند. Provider tableها باید integration projection باشند، مگر اینکه تصمیم معماری خلاف آن را رسماً ثبت کند.</p>

<h2 id="stock-model">Stock Model</h2>
<br />
<p><code class="code-inline">StockBalanceEntity</code> یک composite identity دارد:</p>

<p>- company</p>
<p>- warehouse</p>
<p>- SKU</p>

<p>مقادیر زیر جدا نگهداری می‌شوند:</p>
<br />
<p>- on hand</p>
<p>- available</p>
<p>- reserved</p>
<p>- damaged</p>
<p>- QC hold</p>
<p>- blocked</p>
<p>- in transit</p>
<br />
<p>وجود <code class="code-inline">@Version</code> optimistic locking را در سطح Entity فراهم می‌کند.</p>
<br />
<h2 id="inventory-posting">Inventory Posting</h2>
<br />
<p><code class="code-inline">InventoryPostingService</code> رفتارهای transactional زیر را دارد:</p>
<br />
<p>- Receipt؛</p>
<p>- Transfer؛</p>
<p>- Adjustment؛</p>
<p>- انتقال Available به QC Hold؛</p>
<p>- QC PASS به Available؛</p>
<p>- QC FAIL به Damaged یا Blocked؛</p>
<p>- ثبت Stock Ledger.</p>
<br />
<h2 id="reservation">Reservation</h2>
<br />
<p><code class="code-inline">ReservationService</code>:</p>
<br />
<p>- quantity مثبت را validate می‌کند؛</p>
<p>- balanceهای tenant/company/warehouse/SKU را می‌خواند؛</p>
<p>- اولین balance دارای available کافی را انتخاب می‌کند؛</p>
<p>- Available را کم و Reserved را زیاد می‌کند؛</p>
<p>- Reservation با state <code class="code-inline">ACTIVE</code> می‌سازد؛</p>
<p>- در Release مقدار آزادشدنی را به Available برمی‌گرداند.</p>
<br />
<p>Classification: <code class="code-inline">IMPLEMENTED_WITH_GAP</code>.</p>
<br />
<h2 id="-">نقاط قوت</h2>
<br />
<p>- stock states صریح و تفکیک‌شده؛</p>
<p>- tenant/company در composite key؛</p>
<p>- optimistic locking؛</p>
<p>- ledger دارای source و idempotency field؛</p>
<p>- insufficient-stock check برای reservation و QC hold؛</p>
<p>- Reservation Entity مستقل.</p>
<br />
<h2 id="gap-">Gapهای بحرانی</h2>
<br />
<p>1. Controller، tenant، company و user را از query parameter می‌گیرد؛ این اطلاعات authority قابل اعتماد نیستند.</p>
<p>2. <code class="code-inline">GET /stock/ledger</code> در Controller بررسی‌شده بدون tenant filter است.</p>
<p>3. Posting APIهای عمومی در همان Controller دیده نشدند و caller/orchestration هنوز verify نشده است.</p>
<p>4. idempotency key در ledger ذخیره می‌شود، اما قبل از balance mutation duplicate lookup انجام نمی‌شود.</p>
<p>5. Transfer و Adjustment می‌توانند quantity منفی بسازند.</p>
<p>6. Reservation اولین balance مناسب را بدون policy مشخص انتخاب می‌کند.</p>
<p>7. retry strategy برای optimistic-lock conflict پیدا نشد.</p>
<p>8. Receipt، good quantity را فوراً Available می‌کند و quarantine/quality gate اجباری ندارد.</p>
<p>9. Event/outbox برای Inventory facts پیدا نشد.</p>
<p>10. Provider WMS و Warehouse Receiving با Inventory ownership مرز روشن ندارند.</p>
<br />
<h2 id="-">اصلاح لازم</h2>
<br />
<p>Warehouse Receipt باید ورودی governed برای Inventory باشد. Availability باید با Policyهایی مانند Quality، Quarantine، Lot، Expiry، Compliance و Channel Eligibility محاسبه شود؛ نه صرفاً با receipt فیزیکی.</p>
